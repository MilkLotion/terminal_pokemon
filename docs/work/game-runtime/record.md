## 설계

### 실제 앱을 저장 v3 으로

날짜: 2026-09-24. 사용자 지시: “커밋하고 실제 앱에 v3 연결해봐”. 지금까지 만든 v3 을 실제로 도는 앱에 붙였다.
이 작업은 설계 절을 따로 적지 않고 시작했다. 아래는 작업 뒤에 적은 판단이다.

**저장 하나** — v3 은 따로 두었던 `save-v3.json` 을 버리고 기존 `save.json` 을 쓴다. 처음 열 때 v2 를 v3 으로 옮기고 원본을 `save.json.v2.bak` 에 남긴다. 두 저장이 함께 살면 관리 창에서 밥을 주고 바탕화면에서는 굶는 일이 생긴다. 그래서 반쪽 연결을 하지 않고 한 번에 넘겼다.
`createGame` 에 `canWrite` 를 더했다. `save.lock` 을 잡은 프로세스만 쓴다. reader 는 읽기만 하고 명령은 mailbox 로 보낸다 (docs/specs/modules.md "저장 쓰기는 주 프로세스 하나가 한다").
SSOT: `docs/specs/s5.md` 의 화면 구조와 저장, `docs/specs/modules.md` 의 저장 구조.

### 끊긴 기능 세 가지의 v3 설계

날짜: 2026-09-24. 상태: 구현·검수 완료. 사용자 지시: "A로 진행해". 설계 승인: "진행해".
대상은 v3 전환에서 끊긴 에이전트 보상, 모습 선택, 찌르기다. [실제 앱을 저장 v3 으로](#실제-앱을-저장-v3-으로)의 "끊긴 것"을 닫는다.

**사용자 결정** (2026-09-24)
- 에이전트 보상: 작업 시간 기준. 원문 선택지는 "작업 시간 기준 (권장)"이다.
- 찌르기: 원문은 "포켓몬클릭이 놀아주기인데?"다. 계약도 같다(`docs/specs/s5.md` "직접 돌봄 — 클릭 한 번으로 반응을 구경한다"). 찌르기는 따로 두지 않는다.
- 별명·모습: 계약대로 제거. 원문 선택지는 "계약대로 제거 (권장)"다.

**목표**
1. 에이전트가 작업하는 동안 파티 개체의 시간 적립이 2배가 된다. 기본 적립에 더하는 추가 이득이다. 상한을 두지 않는다.
2. 포켓몬을 클릭하면 놀아주기를 한다. 쿨타임이면 반응만 보인다.
3. 무대는 실제 종의 이름과 그림을 보인다. 옛 별명과 모습은 `legacy` 에 보존만 한다.

**범위**
- 에이전트 보상: `applyTime` 이 작업 시간(`workMs`)을 받는다. 작업 시간만큼 친밀도 진행과 포인트 진행을 한 번 더 쌓는다. 배율(버프·만복도 구간)은 기본 적립과 같다. 파티 칸의 개체만 받는다. 숨김도 받는다. 박스는 받지 않는다. 받은 친밀도는 `daily.work` 에 더한다.
  작업 판정은 v2 와 같다. 무대의 에이전트 상태가 `running` 인 시간이다. writer 의 15초 틱이 판정한다. 토큰량은 보상 계산에 쓰지 않는다.
- 클릭: 무대 클릭은 `play` 명령을 보낸다. 성공하면 놀아주기 연출을 보인다. 실패하면(쿨타임·세션 펫) 클릭 반응만 보인다. `poke` 명령은 반응만 하는 명령으로 남긴다. CLI 호환 때문이다.
- 모습: `src/main/party-v3.ts` 가 `legacy` 의 `look:<id>`·`nick:<id>` 를 읽지 않는다. `pet.look` 은 `removed` 로 답한다.
  같은 날 검수 #4 의 "진화하면 `look:<id>` 를 옮긴다"는 무대가 legacy 모습을 읽을 때만 필요했다. 이번 변경 뒤에는 필요 없으므로 되돌린다. 검사 `selftest-evolve` (11)도 함께 지운다.

**SSOT**: `docs/specs/s5.md` (종료와 재개 뒤의 전환 문단, 직접 돌봄), `docs/specs/balance.md` (버프와 친밀도), `docs/design.md` (적립 표), `docs/terms.md` (작업 시간).

**위험**
- 작업 판정이 무대의 에이전트 상태에 기댄다. 상태가 `running` 으로 남으면 보너스가 계속 쌓인다. v2 와 같은 위험이다.
- 클릭이 놀아주기가 되면 끌기 뒤의 클릭도 놀아주기가 될 수 있다. 무대가 끌기와 클릭을 구분하는지 작업에서 확인한다.
- 옛 별명을 쓰던 사용자는 무대 이름이 종 이름으로 바뀐다. 값은 `legacy` 에 남는다.

**수용 검사**
1. `selftest-time-v3`: 작업 시간이 친밀도·포인트 진행을 2배로 만든다. 작업 시간은 흐른 시간을 넘지 않는다. 박스 개체는 받지 않는다. `daily.work` 에 기록한다.
2. `selftest-manage`: `game.tick` 에 작업 여부를 주면 적립이 늘어난다.
3. 클릭 처리 검사: 놀아주기 성공 시 연출, 쿨타임 시 반응만, 세션 펫은 반응만.
4. `selftest-stage`: v2 에서 옮긴 개체가 종 이름과 종 그림으로 나온다. `legacy` 값은 남는다.
5. `pet.look` 이 `removed` 로 답한다.
6. `npm run selftest`, `node scripts/e2e-companion.cjs` 통과.
7. 문서: 에이전트 보상 수치를 `balance.md` 에 적는다. `s5.md` 의 `[스펙 미확정]` 문장을 닫는다. `design.md` 의 v2 토큰 적립 표를 v3 기준으로 고친다.

**이번 범위 밖으로 관측한 것**
- v3 에는 기분이 바뀌는 규칙이 없다. 우클릭 메뉴의 기분이 늘 같다.
- `docs/design.md` 와 `docs/terms.md` 의 오래 놀아주기 설명(10초 안에 이어 누르며 약 30초)이 구현된 3중첩 규칙과 다르다.

### 옛 v2 코드 정리의 설계

날짜: 2026-09-25. 상태: 커밋 1 `9aa6241`. 커밋 2 작업·검수 완료. 사용자 지시: "진행" ([작업 후보](../../progress.md#작업-후보) 2번). 설계 승인: "진행".

**관측** (제품 진입점에서 import 를 따라간 결과. 진입점은 `src/main/app.ts`, `preload.ts`, 렌더러, `src/cli/game.ts`, 훅, `cli/*.js` 가 부르는 `dist/` 모듈이다)
- 앱과 CLI 가 쓰지 않는 모듈 5개: `src/dex/progress.ts`, `src/main/game-menu.ts`, `src/shop/catalog.ts`, `src/shop/core.ts`, `src/state/core.ts`. 검사 `selftest-shop`·`selftest-state`·`smoke-renderer` 만 쓴다.
- 쓰는 모듈 안의 v2 전용 코드: `src/main/party.ts` 의 `createSaveParty` 와 도움 함수, `src/main/paths.ts` 의 `readSavedWindows`, `src/main/text.ts` 의 `stateLine`, `src/main/commands.ts` 의 `PartySource | V3Party` 갈래.
- **결함**: `cli/run.js` 와 `cli/status.js` 가 저장을 v2 읽기(`dist/save/store.js`)로 읽는다. v3 저장을 v2 로 읽으면 "파손"이 된다(임시 v3 파일로 확인). 그래서 2026-09-24 전환 뒤 `pokebuddy status` 는 늘 "저장이 깨짐"을 보이고, `pokebuddy companion` 은 늘 "첫 실행" 안내를 보인다. 저장 파일은 바뀌지 않는다(`repair: false`).
- `selftest-stage` 의 저장 잠금·reader·writer 검사 대부분이 `createSaveParty`(v2)를 본다. `createV3Party` 는 같은 일을 하지만 검사가 적다.

**목표**
1. CLI 가 v3 저장을 바르게 읽는다.
2. 앱이 쓰지 않는 v2 코드를 걷는다. v1·v2 저장을 v3 로 옮기는 길은 남긴다. 옛 저장을 가진 사용자의 진행을 지키기 위해서다.
3. "새 코드"를 뜻하던 `-v3` 꼬리표를 파일·함수 이름에서 뗀다. 저장 형식 자체를 가리키는 이름(`SaveV3`, `PetV3`, `SAVE_V3_RULES`, `save/v3.ts` 의 뜻)은 남긴다. [번호 체계](../../terms.md#번호-체계)와 맞춘다.

**범위** — 커밋 두 개로 나눈다.
- 커밋 1 (동작): CLI 수정, 죽은 모듈 5개와 v2 전용 함수 제거, 관련 검사 정리. `selftest-stage` 의 v2 잠금 검사는 `createV3Party` 로 옮겨 같은 성질(reader 는 쓰지 않는다, 창 펫은 독립 펫에 자리를 내준다, 잠금을 다시 잡는다)을 본다. `smoke-renderer` 는 v2 메뉴 부분을 뺀다.
- 커밋 2 (이름): 파일 이름 변경. 안: `main/game-v3.ts`→`main/game.ts`, `main/party-v3.ts`→`main/save-party.ts`, `main/status-v3.ts`→`main/status.ts`, `state/time-v3.ts`→`state/time.ts`, `state/care-v3.ts`→`state/care.ts`, `state/settings-v3.ts`→`state/settings.ts`, `shop/catalog-v3.ts`→`shop/catalog.ts`, `save/store.ts`→`save/legacy.ts`(v1·v2 읽기), `save/store-v3.ts`→`save/store.ts`, 검사 `selftest-*-v3` 도 같게. 함수 `createV3Party`·`V3Party`·`saveFileV3` 도 뗀다. 문서의 경로 링크를 함께 고친다.

**범위 밖** — 타입과 규칙표 이름(`SaveV3` 등), 데이터 파일, `lib/i18n` 의 쓰지 않게 된 문구 키(따로 정리).

**위험**
- 잠금 검사를 옮기다 빠뜨리면 여러 창의 저장 충돌을 못 잡는다. 옮기기 전 검사 이름 목록을 적고 옮긴 뒤 대조한다.
- 이름 변경이 문서 링크 수십 개를 바꾼다. `check-docs` 와 앵커 확인으로 잡는다.
- `cli/*.js` 는 타입 검사를 받지 않는다. 임시 HOME 으로 `pokebuddy status` 를 실제로 돌려 확인한다.

**수용 검사**
1. 임시 HOME 의 v3 저장으로 `pokebuddy status` 가 포인트·파티를 보이고 "깨짐"을 보이지 않는다. 저장이 없으면 "저장 없음"이다.
2. `pokebuddy companion` 의 첫 실행 판정이 v3 저장을 본다 (E2E 로 확인).
3. 진입점에서 닿지 않는 모듈이 `src/tools` 밖에 없다 (같은 import 추적).
4. v1·v2 저장을 여는 검사(`selftest-save`, `selftest-save-v3`, `selftest-stage` 이전 검사)가 통과한다.
5. 옮긴 잠금 검사가 옛 검사의 성질을 모두 본다.
6. `npm run build`, `npm run selftest`, `node scripts/e2e-companion.cjs`, `node scripts/check-docs.cjs` 통과.
7. 커밋 2 뒤 `src` 파일 이름에 `-v3` 가 없다.

### 기분 규칙의 설계

날짜: 2026-09-25. 상태: 구현·검수 완료. 사용자 지시: "4번 먼저 하고 3번 진행". 승인: "4번 커밋하고 기분 규칙 진행". [작업 후보](../../progress.md#작업-후보) 3번이다.
사용자 결정: "표시만, 간단한 규칙 (권장)". 선택지 설명은 "밥 주기·놀아주기로 오르고, 시간이 지나면 천천히 내려가며, 배고프면 더 빨리 내려간다. 게임 수치에는 영향을 주지 않는다"였다.

**관측** (2026-09-25)
- 기분(`PetV3.mood`, 0~100)을 바꾸는 코드가 없다. 새 개체는 60 으로 시작해 계속 60 이다.
- 기분을 읽는 곳은 우클릭 메뉴 상태 줄(`src/main/status.ts`)과 `pokebuddy status` 둘이다. 다른 수치에 영향을 주지 않는다.
- 계약: `terms.md` "기분은 오르내릴 수 있다", "놀아주기는 기분과 친밀도에 영향을 준다". `specs/s5.md` 화면 표 "상세 — … 친밀도, 기분 …". 지금 관리 창 상세에는 기분이 없다.
- 기분 단계 말은 `lib/i18n.js` 의 `moodWord` 다. 80 이상 최고, 60 이상 좋음, 40 이상 보통, 20 이상 시들, 그 아래 우울.

**목표** — 돌보면 기분이 오르고 내버려 두면 내려간다. 기분은 보이기만 하고 다른 수치를 바꾸지 않는다.

**수치** (사용자 승인: "4번 커밋하고 기분 규칙 진행". 제안 그대로 승인)

| 항목 | 값 |
|---|---|
| 시작 | 60 (좋음). 지금과 같다 |
| 밥 주기 | +10. 기본먹이·프리미엄먹이 모두 |
| 놀아주기 | +15. 클릭 놀아주기와 장난감 모두 |
| 시간 감소 | 파티 칸 개체는 10분에 1 (시간당 6). 숨김도 같다. 박스는 멈춘다 |
| 배고픔 | 배고픔 구간은 감소 2배, 매우 배고픔은 3배 |
| 범위 | 0~100 |

환산: 100 에서 돌보지 않으면 약 6시간 40분 뒤 60(좋음 → 보통 경계)이 된다. 놀아주기 쿨타임(10분)마다 놀아주면 줄지 않는다. 앱이 꺼진 동안은 흐르지 않는다(다른 시간 규칙과 같다).

**범위**
- `src/state/time.ts`: 파티 칸 개체의 기분을 만복도처럼 부분 진행(ms)으로 줄인다. 새 필드 `moodProgressMs` 를 `PetV3`·정규화·새 개체·v2 이전에 더한다.
- `src/state/care.ts` 놀아주기, `src/bag/use.ts` 먹이·장난감 효과에서 기분을 올린다.
- 화면: 스냅샷에 기분 값과 단계 말을 더한다. 관리 창 개체 상세에 기분 막대를 더한다. 우클릭 메뉴와 CLI 는 이미 기분을 보인다.
- 문서: `balance.md` 에 기분 행을 더한다. `terms.md`·`s5.md` 의 기분 문장을 이 규칙에 맞춘다.

**범위 밖** — 기분이 친밀도·포인트·움직임에 주는 효과. 성격별 보정(옛 v2 에 있었다).

**위험**
- 저장 필드를 하나 더한다. 옛 저장에는 없으므로 정규화가 0 으로 채워야 한다.
- 기분 감소가 배고픔 구간 판정을 따르므로 만복도 감소 뒤의 구간으로 셈한다(친밀도와 같은 순서).

**수용 검사**
1. `selftest-time`: 파티 개체는 10분에 1 줄고, 배고픔·매우 배고픔에서 2배·3배다. 박스 개체는 줄지 않는다. 0 아래로 가지 않는다. 짧은 틱 여러 번과 긴 틱 한 번이 같다.
2. `selftest-bag`: 놀아주기 +15, 먹이 +10, 장난감 +15, 100 을 넘지 않는다.
3. `selftest-save`: `moodProgressMs` 가 없는 저장을 0 으로 읽는다.
4. `selftest-snapshot`: 기분 값과 단계 말이 스냅샷에 있다.
5. 관리 창 상세에 기분 막대가 보인다(개발용 실행기 화면).

### 관리 창 — 진화 확인과 후보 고르기의 설계

날짜: 2026-09-25. 상태: 구현·검수 완료. 사용자 지시: "다음작업 하나씩 진행하자". 설계 승인: "진행.". [작업 후보](../../progress.md#작업-후보) 5번(관리 창 남은 화면)을 넷으로 나눈다. 순서는 막힌 기능부터다: ① 진화 확인과 후보 고르기 ② 민트 성격 고르기 ③ 도감 상세 ④ 검색 줄. 이 절은 ①이다.

**관측** (2026-09-25)
- 상세의 `진화` 를 누르면 확인 없이 곧바로 진화한다. 후보가 둘 이상이면 `need-choice` 로 끝나고 "고르는 화면이 아직 없습니다"를 보인다. 이브이는 늘 여기서 막힌다.
- 가방에서 진화의돌을 쓰면 `no-item` 으로 실패한다. `bag.use` 가 진화용 도구를 모른다(임시 저장으로 확인). 상세의 `진화` 는 돌을 조건으로 쓰고 하나를 소비한다.
- 스냅샷에 진화 후보가 없다. 화면은 무엇으로 진화할 수 있는지, 무엇이 모자란지 모른다.
- 계약: "분기의 조건을 둘 이상 충족하면 가능한 후보를 보여주고 사용자가 선택한다"(`specs/s5.md`). "진화 확인 화면에서 취소한 개체는 진화 가능 상태를 유지한다"([기록](../s5-design-system-v2/plan.md)). "가방에서 진화의돌과 대상 개체를 고르면 진화 확인 화면으로 이어진다. 확인하면 진화하고 돌 1개를 소비한다"(`specs/s5-scenarios.md`). 확인 화면은 대화상자(C-13)와 정보 상자(C-25)를 쓴다(`specs/ui-components.md`).

**목표**
1. 상세의 `진화` 가 진화 확인 창을 연다. 후보마다 결과 종과 상태(가능 / 모자란 조건)를 보인다. 가능한 후보가 하나면 그것을, 둘 이상이면 사용자가 고른 것을 `확인` 으로 진화한다. `취소` 는 아무것도 바꾸지 않는다.
2. 가방에서 진화의돌을 누르면 그 돌로 지금 진화할 수 있는 개체 목록이 나온다. 고르면 같은 진화 확인 창으로 이어진다. 확인하면 진화하고 돌 1개를 쓴다.
3. 진화할 곳이 없는 종(최종 단계)의 상세에는 `진화` 를 두지 않는다.

**범위**
- 스냅샷 `PetView.evolutions`: 후보마다 `to`(종), `name`(화면 이름), `ready`, `need`(모자란 조건의 화면 문구. 예: "Lv.16 필요", "친밀도 65 필요", "물의돌 필요", "밤에만"), `item`(돌 조건이면 도구 id). 낮·밤은 스냅샷을 만드는 시각으로 정한다.
- 관리 창: 진화 확인 창(후보 행 + 정보 상자 "지금 → 결과" + `취소`·`진화`). 가방의 진화용 도구 행은 대상 고르기를 거쳐 이 창을 연다.
- 명령은 이미 있다. `evolve` 가 `args.to` 를 받고, 그림을 먼저 받아 둔다. 새 명령을 만들지 않는다.

**범위 밖** — 진화 연출 화면(무대의 축하 연출은 이미 있다), 코스모움처럼 두 종을 함께 주는 특수 진화, 진화 가능 배너(작업 후보 6번).

**위험**
- 스냅샷이 시각을 쓰게 된다. 검사가 흔들리지 않게 시각을 인자로 받는다(기본은 지금).
- 돌 조건의 후보는 가방에 돌이 없으면 모자란 조건으로 보인다. 가방 경로와 상세 경로가 같은 판정을 쓰는지 확인한다.

**수용 검사**
1. `selftest-snapshot`: 불꽃의돌을 가진 이브이의 `evolutions` 에서 부스터만 가능하다. 나머지는 모자란 조건 문구가 있다. 최종 단계 종은 빈 목록이다. 밤 시각이면 블래키 조건이 달라진다.
2. 개발용 실행기 화면: 상세 `진화` → 확인 창이 후보와 조건을 보인다. `취소` 뒤 저장이 그대로다. 가방의 돌 → 대상 → 확인 창으로 이어진다.
3. `npm run selftest`, `node scripts/e2e-companion.cjs`, `node scripts/check-docs.cjs` 통과.

### 관리 창 — 성격별 민트의 설계

### 알림 배너의 설계

날짜: 2026-09-25. 상태: 구현·검수 완료. 사용자 지시: "커밋하고 다음거 진행." 설계 승인: "진행". 작업 후보 6번이다.

**관측** (2026-09-25)
- 지금은 `src/main/app.ts` 의 `notifyTick` 이 OS 알림을 띄운다. 부화는 알 개수와 무관하게 한 번, 업적은 업적마다 한 번이다. 진화 가능 알림은 없다.
- 계약: `specs/s5.md` "알림 배너의 개별 표시", `specs/ui-components.md` C-19, `specs/modules.md` `src/notify`(줄 세우기·한 번 규칙·순서만, 상태 판정은 도메인 모듈).
- Figma: 부품 `Notification Banner` `338:732`(폭 280, `Type=Achievement|Hatch|Evolution`). 화면 `Playground / Banner Hatch` `395:8492` 등은 바탕화면 오른쪽 아래에 배너를 둔다.
- 진화 판정은 `src/dex/evolve.ts` 의 `canEvolve` 가 이미 있다. 설정 `settings.sound` 와 관리 창의 "알림 소리" 토글도 이미 있다.
- 저장 v3 에 배너 상태 칸이 없다. 계약은 "배너 상태의 저장 구현"을 미정으로 둔다.

**목표**
1. 새 모듈 `src/notify`: 매 틱 저장을 훑어 미처리 상태 목록을 만든다. 부화 준비 알(돌보미집 순서) → 진화 가능 개체(파티 칸 → 박스 순서) → 미수령 업적(업적창 순서).
2. 대상 키: `hatch:<알 id>`, `evolve:<개체 id>:<지금 종>`, `achievement:<업적 id>`. 진화 키에 종을 넣는다. 한 번 진화한 뒤 다음 단계가 가능해지면 새 배너가 뜬다.
3. 표시한 키와 대기 줄을 저장한다. 표시한 키는 다시 줄에 넣지 않는다. 줄에 있는 동안 상태가 풀리면 뺀다. 대상이 사라지면(알 부화, 종 변경, 보상 수령) 표시한 키도 지운다.
4. 배너 창: 테두리 없는 작은 창을 주 화면 작업 영역 오른쪽 아래에 띄운다. 항상 위, 포커스를 뺏지 않음, 작업 표시줄에 없음. 한 번에 하나씩 보인다.
5. 문구: 제목(`부화 준비 완료` / `진화 가능` / `업적 달성`), 대상(`돌보미집 알 N` / `<이름> Lv.N` / 업적 이름), `바로가기`. 결과 종은 보이지 않는다.
6. `바로가기`: 관리 창을 열고 부화는 박스 탭의 돌보미집, 진화는 그 개체 상세, 업적은 업적 창으로 간다. 관리 창이 열려 있으면 그 창을 앞으로 가져와 옮긴다.
7. 소리: `settings.sound` 가 켜져 있으면 배너를 띄울 때 `shell.beep()`(OS 기본 알림음)를 낸다. 무음이어도 배너와 이동은 그대로다.
8. 부화·업적의 OS 알림을 없앤다. 명령 실패 알림(`game.failed`)은 OS 알림으로 둔다.

**제안 값** (`[스펙 미확정]` 을 이번 구현에서 정하는 값)
- 표시 시간 8초. 배너 위에 커서가 있으면 멈춘다. 닫기 단추는 두지 않는다(계약: 누르지 않으면 사라진다).
- 다중 화면: 주 화면 기준.
- 배너 상태 저장: 저장 v3 가 아니라 같은 폴더의 `notify.json` 에 둔다. 배너는 게임 상태를 바꾸지 않기 때문이다(계약: "배너 폐기는 대상의 게임 상태를 바꾸지 않는다"). 쓰는 쪽은 writer 프로세스 하나다. 저장이 실패하면 배너는 보이고 다음 틱에 다시 쓴다.
- 처음 켤 때(파일이 없을 때) 이미 미처리인 상태는 표시한 것으로 둔다. 업데이트 직후 배너가 한꺼번에 몰리지 않게 한다.

**범위 밖** — 배너 안의 그림(부화 알·개체 그림은 Figma 처럼 점 모양으로 둔다), OS 무음·집중 모드 연동, 다중 화면 선택.

### Windows 실행 파일의 설계

날짜: 2026-09-25. 상태: 구현·검수 완료, 실제 설치는 사용자 확인 대기. 사용자 요청: "exe파일같은 실행파일로 있음 좋을거같은데". 새 패키지 `electron-builder`(개발용) 추가 승인: "진행". 설계 승인: "진행". 작업 후보 10번(S6 배포)의 첫 부분이다.

**관측** (2026-09-25)
- 지금 설치는 `npm install -g pokebuddy` 뿐이다. Node.js 22.12 이상이 필요하다. 동반자는 `pokebuddy companion` 으로 띄운다.
- 실행 모드는 `POKEBUDDY_MODE` 환경 변수로 정한다. 없으면 `session` 이다(`config.js`). 세션 펫은 부른 터미널이 끝나면 함께 끝나므로 더블클릭 실행에 맞지 않는다.
- 동반자를 직접 실행하면 앱이 `companion.lock` 을 스스로 만든다(`src/main/lifetime.ts` `claim`). 두 번째 실행은 단일 인스턴스 잠금으로 바로 끝난다.
- 앱은 파일을 `config.js` 가 있는 폴더 기준으로 찾는다(`PATHS.project`). 그림·데이터·HTML·`helpers/winbounds.ps1`·`cli/setup.js`·`dist/hooks` 가 모두 그 아래에 있어야 한다.
- 로그인 시 시작 설정(`settings.startOnLogin`)은 저장만 되고 OS 에 적용하는 코드가 없다.
- 상태 훅은 `node "<경로>"` 로 등록된다(`cli/setup.js` `hookCommand`). 훅을 쓰려면 Node.js 가 필요하다.
- `electron` 은 `dependencies` 에 있다. npm 판 CLI 가 실행 때 쓰기 때문이다. `electron-builder` 는 앱의 `dependencies` 에 `electron` 이 있으면 묶기를 거부한다.
- 로고 `assets/logo/out/logo.ico` 가 있다.

**목표**
1. `npm run dist:win` 한 번으로 `release/pokebuddy-Setup-<버전>.exe` 를 만든다.
2. 설치 파일: 사용자 폴더에 설치(관리자 권한 없음), 설치 위치 선택 가능, 시작 메뉴·바탕화면 바로가기, 제거 프로그램 등록. 제거해도 저장 폴더(`~/.claude/pokebuddy`)는 지우지 않는다.
3. 설치한 앱을 실행하면 동반자 모드로 뜬다. 첫 실행이면 포켓몬 선택 창이 뜬다. 트레이 아이콘이 생긴다.
4. 앱이 이미 떠 있을 때 다시 실행하면 새로 띄우지 않고 관리 창을 연다.
5. 설정의 "로그인 시 시작"을 OS 에 적용한다. 설치한 앱에서만 적용한다 — 저장소에서 `electron .` 으로 띄운 앱을 등록하면 빈 Electron 이 뜨기 때문이다.
6. 저장 폴더는 npm 판과 같다. 두 판이 같은 파티와 포인트를 본다.

**방법**
- `scripts/build-exe.cjs`(신규): ① `npm run build` ② `release/app/` 에 실행에 필요한 파일만 복사하고, 의존성이 없는 작은 `package.json`(이름·버전·`main`)을 만든다 ③ `electron-builder` API 로 `release/app` 을 묶는다. Electron 버전은 루트 `package.json` 의 `electron` 값을 쓴다. 이렇게 하면 루트의 `dependencies` 를 바꾸지 않는다.
- 복사할 파일은 루트 `package.json` 의 `files` 목록과 같다. `vscode-extension`·`*.tgz`·빌드 도구는 뺀다.
- asar 로 묶지 않는다. 훅 원본 복사, PowerShell 도우미, `cli/setup.js` 가 실제 파일 경로를 쓰기 때문이다.
- `config.js`: 설치한 앱(`process.defaultApp` 이 없는 Electron)이고 `POKEBUDDY_MODE` 가 없으면 기본 모드를 `companion` 으로 한다. 저장소 실행과 npm 판은 지금과 같다.
- `src/main/app.ts`: 동반자의 `second-instance` 에서 관리 창을 연다. 설치한 앱이면 시작할 때와 설정이 바뀔 때 `app.setLoginItemSettings({ openAtLogin })` 를 부른다.
- `package.json`: `devDependencies` 에 `electron-builder`, 스크립트 `dist:win`. `.gitignore` 에 `release/`.

**범위 밖**
- 코드 서명. 서명하지 않은 exe 는 처음 실행 때 SmartScreen 경고가 뜬다("추가 정보 → 실행").
- mac dmg, 자동 업데이트, 배포 사이트 게시.
- exe 판에서 세션 펫(`!pokebuddy eevee`)과 VS Code 창 펫. 이 둘은 npm 판으로 쓴다.
- Node.js 없이 도는 상태 훅. 첫 판은 훅에 Node.js 가 필요하다. 없는 경우의 안내는 따로 정한다.
- 로그인 시 시작의 기본값(계약은 켜짐, 저장 기본값은 꺼짐). 작업 후보 7번에서 정한다.

**SSOT 파일** — `scripts/build-exe.cjs`(신규), `package.json`, `package-lock.json`, `.gitignore`, `config.js`, `src/main/app.ts`, `docs/guide.md`(설치 안내), `README.md`(설치 절).

**위험**
- `electron-builder` 는 빌드할 때 NSIS 와 Electron 파일을 인터넷에서 받는다. 오프라인에서는 빌드가 실패한다.
- 실제 설치는 사용자 PC 의 프로그램 목록·바로가기·레지스트리를 바꾼다. 설치 확인은 사용자 승인 뒤에 한다.
- 설치 폴더를 바꿔 다시 설치하면 등록된 훅 경로는 영향을 받지 않는다. 훅은 `~/.claude/scripts/hooks` 로 복사해서 쓰기 때문이다.

**수용 검사**
1. `npm run dist:win` 이 설치 파일과 `release/win-unpacked/pokebuddy.exe` 를 만든다.
2. 임시 HOME 으로 `win-unpacked/pokebuddy.exe` 를 띄우면 동반자로 뜨고, 임시 폴더에 저장과 `companion.lock` 이 생긴다(`POKEBUDDY_SLUG` 로 선택 창을 건너뛴다). 두 번째 실행은 바로 끝난다.
3. `npm run selftest`, `node scripts/e2e-companion.cjs`, `check-docs` 통과.
4. 사용자 확인: 설치 파일로 설치 → 바로가기 실행 → 제거.

### 설치 창과 첫 포켓몬 선택 창의 설계

**관측** (2026-09-25)

**목표**

2. 선택 창: Figma 대로. 제목 `첫 포켓몬 선택`, 부제, 5열 카드, 고른 카드 표시, 아래 줄(고르기 전 `포켓몬을 고르세요`, 고른 뒤 이름과 `진화: …`), `함께하기`. 기본 메뉴를 없앤다. 창은 640×780 이고 카드 목록만 스크롤한다.

**범위 밖** — 카드 초상의 실제 그림(관리 창도 원만 그린다), 다크 모드(관리 창과 맞춰 뺐다).

**수용 검사** — 개발용 실행기로 빈 상태·고른 상태를 찍어 Figma 와 비교, E2E 의 첫 선택 흐름 통과, 설치 파일이 `oneClick=true` 로 만들어짐.

### 놀이공간·설정의 설계

날짜: 2026-09-25. 상태: 구현·검수 완료, 실제 사용 확인 대기. 사용자 지시: "다음거 진행". 설계 승인: "진행". 작업 후보 7번이다. 놀이공간 적용 범위는 사용자가 "동반자만 (권장)"을 두 번 골랐다.

**관측** (2026-09-25)
- 로그인 시 시작: 계약은 기본 켜짐(`specs/s5.md` "설정과 연결")이다. 새 저장의 기본값은 꺼짐이다(`src/save/v3.ts` `empty`). OS 등록은 설치한 앱에서만 한다(Windows 실행 파일 작업).
- 크기: 개체의 `size`(1~6, 기본 2)가 저장에 있고 무대가 그림 배율로 쓴다(`src/main/art.ts` `zoomOf`). `pet.set size` 는 `not-yet` 을 돌려준다(`src/main/commands.ts`). Figma `Detail / Base` 의 "표시 설정" 절에 `크기 1~6` 단추가 있다. 계약은 "조절을 완료하면 한 번 저장한다"이다.
- 놀이공간: 설정 값(`settings.playArea.mode`)만 있고 무대는 쓰지 않는다. 동반자는 맨 앞 터미널 창과 그 화면의 교집합을 무대로 쓴다(`src/main/app.ts` `onAnchorUpdate`). 관리 창 설정에는 `화면 전체 | 영역 지정` 전환만 있고 "영역 그리기는 아직 없습니다"라고 쓴다. Figma `Playground / Region Draw` `396:8541` 에 영역 그리기 화면이 있다.

**목표**
1. 로그인 시 시작: 새 저장과 옛 v1·v2 저장을 옮길 때의 기본값을 켜짐으로 한다. 이미 v3 저장이 있는 사용자의 값은 바꾸지 않는다.
2. 크기: 파티 개체 상세에 "표시 설정" 절(화면 표시·숨기기, 크기 1~6)을 둔다. 크기를 누르면 `pet.set size` 로 한 번 저장하고 무대의 그림 크기가 바로 바뀐다. 박스 개체 상세에는 두지 않는다(계약: 박스 상세에는 표시 항목이 없다).
3. 놀이공간(동반자만):
   - 화면 전체: 동반자의 무대를 터미널 창 대신 주 화면 작업 영역 전체로 둔다. 에이전트 상태는 지금처럼 맨 앞 터미널을 따른다.
   - 영역 지정: 그려 둔 영역을 무대로 둔다. 영역이 어느 화면과도 겹치지 않으면(모니터 변경) 화면 전체로 대신하고 영역 값은 지우지 않는다.
   - 세션 펫과 VS Code 창 펫은 지금처럼 터미널 창을 따른다.
4. 영역 그리기 창(Figma `396:8541`): 커서가 있는 화면을 덮는 투명 창. 화면을 어둡게 하고 드래그로 사각형을 그린다. 크기 표시(`880 × 420`), 미리보기 문구, 아래 도구 막대(`드래그해서 활동 영역을 그리세요`, `다시 그리기`, `취소`, `적용`). Esc 는 취소, Enter 는 적용이다.
5. 관리 창 설정: `영역 지정` 일 때 `영역 그리기`(그린 뒤에는 `다시 그리기`) 단추를 둔다(`specs/s5.md` 설정 계약).
6. 적용하면 영역과 `region` 방식을 한 번에 저장한다. 취소하거나 저장에 실패하면 이전 영역을 유지한다(계약). 구현에서 새 명령 대신 `settings.set` 의 `playRegion` 키로 바꿨다 — 명령 이름·배선 목록을 늘리지 않고 설정 규칙을 한 곳에 둔다.

**제안 값** (`[스펙 미확정]` 을 이번 구현에서 정하는 값)
- 영역 최소 크기 240 × 160. 이보다 작으면 `적용` 을 끈다.
- 영역은 한 화면 안에서만 그린다. 여러 화면에 걸친 영역은 두지 않는다.
- 화면 전체는 주 화면 기준이다.
- 동반자는 놀이공간 설정을 게임 틱(15초)마다, 그리고 관리 창에서 설정을 바꾼 직후에 다시 읽는다.

**범위 밖** — 놀이공간 튜토리얼(튜토리얼 화면 전체가 미구현), 세션·창 펫의 놀이공간, 여러 화면 선택.

**SSOT 파일** — `src/save/v3.ts`, `src/state/settings.ts`, `src/main/commands.ts`·`save-party.ts`(크기), `src/main/app.ts`(무대 사각형), `src/main/region-window.ts`·`src/renderer/region.html`·`region.ts`(신규), `src/main/manage-window.ts`·`preload.ts`·`src/shared/manage.d.ts`·`src/renderer/manage.ts`·`manage.html`, 자체 검사, `docs/specs/s5.md`.

**위험**
- 무대가 화면 전체가 되면 투명 창이 화면 전체를 덮는다. 지금처럼 그림 위에서만 클릭을 받고 나머지는 통과시키는지 확인한다.
- 저장된 집(`home`)은 무대 오른쪽 아래 기준 오프셋이다. 무대가 터미널 창에서 화면 전체로 바뀌면 처음 자리가 바뀐다.
- 관리 창과 영역 그리기 창은 다른 세션도 고치는 파일을 건드린다. 고치기 전에 알린다.

## 작업

### 저장 v3 전환의 작업

**만든 파일** — `src/main/party-v3.ts`(무대가 보는 마리 목록), `src/main/status-v3.ts`(우클릭 메뉴의 상태 문구), `src/party/create.ts`(개체 하나 만들기), `src/party/starter.ts`(첫 선택), `src/party/home.ts`(놓아 둔 자리)다.
`party-v3` 은 저장을 직접 고치지 않는다. 잠금 잡기, 파일 다시 읽기, 무대가 읽을 모양으로 바꾸기 셋만 한다. 변경은 전부 실행기를 거친다.
파일 감시는 writer 와 reader 모두 건다. 자기가 쓴 것도 감시로 돌아와 읽으므로 메모리와 파일이 갈라지지 않는다.
개체 생성이 알 열기와 종 구매 두 곳에 각각 적혀 있었다. `newPet` 하나로 모으고 첫 선택도 같은 것을 쓴다.

**명령** — 저장을 바꾸는 명령은 전부 실행기로 간다. `src/main/commands.ts` 는 인자를 풀어 넘기고, 무대 반응과 그림 준비만 감싼다.
진화는 바뀔 모습의 그림을 먼저 받아 둔다. 못 받으면 저장을 건드리지 않고 `art-missing` 으로 끝낸다. v2 의 보호를 그대로 옮겼다.
`starter.pick` 과 `pet.set`(자리)을 새로 더했다. 첫 선택은 저장이 비었을 때만 한 번 돈다.
`settings.set` 은 창 표시 항목(hidden·clickThrough·keepVisible)만 여기서 처리하고 나머지 키는 저장으로 넘긴다. 한 이름이 두 곳을 맡는다.

**메뉴** — 트레이와 우클릭의 S4 상점·도감·모습·민트 항목을 걷었다. 관리 창이 그 일을 한다.
우클릭 메뉴는 계약대로 이름·상태 / 밥 주기·놀아주기 / 관리 창 열기 세 묶음이다. 상태 줄은 만복도 구간과 기분 구간을 보여 준다.

**시간** — `stateEngine.tick` + `advance` 를 `game.tick()` 으로 바꿨다. `applyTime` 은 흐른 시간을 받아 계산하므로 저장 주기(15초)마다 한 번 불러도 값이 맞는다.
알 준비 완료와 업적 달성은 OS 알림으로 알린다. 배너 화면은 아직 없다.

**옮기며 고친 것** — v2 가방의 `berry` 가 이름 그대로 넘어와 쓸 수 없는 도구가 됐다. 프리미엄먹이의 옛 이름이므로 옮길 때 `premium-food` 로 바꾼다.

**끊긴 것** — 이 전환으로 v2 의 다음 기능이 멈췄다. [끊긴 기능 세 가지의 v3 설계](#끊긴-기능-세-가지의-v3-설계)에서 닫았다.
에이전트 작업·토큰 보상: v3 시간 처리에 그 입력이 없었다.
모습 선택(`pet.look`): v3 개체에 `look` 이 없다. 옮긴 값은 `legacy` 에 남아 있었고 화면에 그대로 쓰였다. 명령은 `not-yet` 을 돌려줬다.
찌르기(`poke`): 무대 반응만 하고 저장을 바꾸지 않았다.

자체 검사 두 벌이 v2 런타임을 쓰고 있었다. `selftest-stage` 의 명령 왕복과 `selftest-shop` 의 앱 경로를 v3 으로 다시 썼다. v2 규칙 자체를 보는 부분은 그대로 두었다 — 그 모듈들은 아직 트리에 있다.
저장 실패 재현에서 파일을 디렉터리로 바꾸면 읽기도 함께 막힌다. v2 는 메모리 상태가 있어 `save-failed` 였지만 v3 은 읽고 나서 쓰므로 `no-save` 다. 두 경우 모두 실패로 답하는지만 본다.

**검증** — `npm run build` 통과. `npm run selftest` 전체 통과(무대 검사 112건 → 118건). `node scripts/e2e-companion.cjs` 9개 흐름 통과 — 실제 CLI 부터 Electron 종료까지 v3 으로 돈다.
v2 저장을 앱 경로로 열어 옮겨지는지 확인하는 검사를 더했다. 두 마리와 포인트가 그대로 오고, 별명은 `legacy` 에서 되살아나며, 첫 선택을 다시 묻지 않는다. 별명 표시는 끊긴 기능 작업에서 계약대로 뺐다.

**수정**
1·2. 폴링 틈이 `STATE_RULES.maxTickMs`(5초)를 넘으면 세지 않는다. writer 가 아니면 쌓은 값과 폴링 시각을 비운다.
3. 틱이 성공했을 때만 비운다. 실패하면 다음 틱에 흐른 시간과 함께 넘긴다.
4. 옮길 때 `daily.work` 를 0 으로 둔다. `selftest-save-v3` (2b)를 더했다.

### 알림 배너의 피드백과 수정

**피드백**
1. 배너가 바뀔 때 커서가 이미 창 위에 있으면 `mouseenter` 가 다시 오지 않아 새 배너가 멈추지 않았다.
2. 메뉴의 `click: openManageWindow` 가 메뉴 항목을 첫 인자로 넘겨 목적지로 잘못 들어갈 수 있었다.
3. 숨긴 배너 창도 창으로 센다. 무대 창만 따로 닫히면 `window-all-closed` 가 오지 않는다. 관리 창이 열려 있을 때와 같은 동작이다. 무대 창은 앱이 끝날 때만 닫히므로 고치지 않았다.
4. 실제 앱의 배너 흐름, Windows·mac 의 실제 클릭, 알림음은 실기 확인이 필요하다.

**수정**
1. 새 배너를 받을 때 `:hover` 이면 멈춤을 알린다.
2. 두 메뉴 모두 `() => openManageWindow()` 로 감쌌다.
3·4. 남겨 둔다.

### Windows 실행 파일의 피드백

1. 상태 훅은 `node` 로 실행된다. Node.js 가 없는 PC 에서 "연결"을 누르면 등록은 되지만 훅이 돌지 않는다. 첫 판의 범위 밖으로 두었다. 안내 또는 Node 없이 도는 방법은 따로 정한다.
2. `electron-builder` 가 서명 단계(signtool)를 지나지만 인증서가 없어 서명하지 않는다. SmartScreen 경고가 뜬다.
3. `bin/pokebuddy`·`scripts/build-helper.js`·`helpers/winbounds.swift` 는 exe 판에서 쓰지 않지만 `files` 목록을 따라 들어간다. 합쳐 수십 KB 라 두었다.
4. 실제 설치 확인(설치 → 바로가기 → 다시 누름 → 로그인 시 시작 → 제거)은 사용자가 한다.

### 놀이공간·설정의 피드백

1. reader 인 동반자는 게임 틱에서 놀이공간을 다시 읽지 않는다. 자기 관리 창의 설정 변경은 바로 반영한다. 동반자는 보통 writer 라 남겨 둔다.
2. 화면 전체로 바뀌면 저장된 자리(무대 오른쪽 아래 기준)가 터미널 창이 아닌 화면 기준이 되어 처음 자리가 달라진다. 설계의 위험으로 적어 둔 그대로다.
3. 영역 그리기 창은 Windows 에서 작업 표시줄 높이만큼 창이 줄어 잡혔다(3440 × 1440 화면에서 창 높이 1392). 그 아래는 그릴 수 없다.
4. 놀이공간 튜토리얼은 튜토리얼 화면이 없어 범위 밖이다.
